# R46H 62,534,975,488-byte full-card deployment

This flow prepares a larger replacement TF card from the independently frozen
post-recovery p1, p2, and p3 sources. It does not reuse the 31,719,424,000-byte
partition table unchanged. The larger card has this exact geometry:

- g92/MBR prefix: offset 0, size 16,777,216 bytes;
- BOOT p1: offset 16,777,216, size 117,440,512 bytes;
- Debian 13 p2: offset 134,217,728, size 10,716,877,312 bytes;
- EASYROMS p3: offset 10,851,095,040, size 51,683,880,448 bytes;
- end of p3: exactly 62,534,975,488 bytes.

The p1 and p2 bytes remain identical to the repaired source card. The p3 image
is rebuilt as an exact-size ExFAT filesystem containing the three retained
payload directories (`v0.8`, `v0.9`, and `v0.10`). The new MBR differs from the
repaired 31.7 GB prefix only in the four-byte p3 length field; because one byte
is unchanged, exactly three bytes differ. The expected new prefix SHA-256 is
`3fe2feb9cc89ce5f01603199bfc8b715875708a9acc61bfc68b4821e1d8a5da3`.

## Host build gates

The build must start at a clean tracked HEAD. Temporary image work stays under
external `mainline/out`; the builder never opens a physical block device.

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -B \
  mainline/scripts/build-easyroms-p3-recovery.py \
  --variant fast-card-62534975488

PYTHONDONTWRITEBYTECODE=1 python3 -B \
  mainline/scripts/prepare-r46h-fast-card-assets.py
```

Pin the printed `ASSET_MANIFEST_SHA256`. Before a physical write, confirm live
`diskutil` identity is one USB, external, physical, removable whole disk whose
exact size is 62,534,975,488 bytes. The 1 TB `/dev/disk6` workspace disk is
always rejected.

The write command also requires one exact pre-write factory layout. Use
`factory-fat32-1m` only for a single `Windows_FAT_32` partition at byte
1,048,576 with size 62,533,926,912. Use `factory-exfat-16m` only for the older
single `Windows_NTFS` (Disk Utility's ExFAT content label) partition at byte
16,777,216 with size 62,518,198,272. Any other layout fails before sudo,
unmount, or media access.

## Full-media write

The command is destructive and must name the live whole-disk identifier twice:

```bash
mainline/scripts/provision-debian13-new-card-layout.sh \
  --device /dev/diskN \
  --confirm-device /dev/diskN \
  --layout fast-card-62534975488 \
  --target-before-layout factory-fat32-1m \
  --asset-manifest-sha256 HASH
```

The claimed-media C worker performs these operations in order:

1. pin and full-hash every source;
2. bind the live card geometry and pre-write 16 MiB prefix hash;
3. write the complete BOOT, p2, and 51.68 GB p3;
4. flush both the file descriptor and device cache;
5. write the g92 prefix tail, flush, then write MBR sector 0 last;
6. flush again and fully read/hash all four target ranges;
7. rehash all four source ranges and recheck the raw device identity;
8. publish only `MEDIA_WRITE_COMPLETE`, `safe_to_boot=false`, then eject.

Catchable terminal signals cannot orphan the worker. Once physical writing has
started, the C worker ignores interruption and completes the bounded write,
readback, and cache barriers. A success at this stage is deliberately not a
boot authorization.

## Required post-reinsert audit

Reinsert the same card. Two explicit audit levels are available.

### Quick audit for normal iteration

The recommended first-boot gate is `quick`. It requires the immutable receipt
from the preceding complete write/readback and the exact p3 allocation proof:

```bash
mainline/scripts/audit-debian13-new-card-after-reinsert.sh \
  --device /dev/diskN \
  --confirm-device /dev/diskN \
  --layout fast-card-62534975488 \
  --asset-manifest-sha256 HASH \
  --audit-level quick \
  --prior-write-receipt-dir /ABSOLUTE/.r46h-new-card-layout.RECEIPT \
  --prior-write-status-sha256 STATUS_SHA256 \
  --prior-write-log-sha256 LOG_SHA256
```

It reads 12,199,690,592 raw bytes rather than the entire card twice. Prefix and
BOOT are read repeatedly, p2 is fully compared with its expected hash once,
and the first 256 MiB of p3 is read three times for within-session consistency.
The single p2 read remains on the same claimed, read-only raw descriptor and
validates every p2 byte; a second identical pass would add time but no new
content coverage.

The whole 256 MiB p3 window is deliberately not required to match the original
image byte-for-byte. A normal macOS automount may add `.Spotlight-V100` or
`.fseventsd`, which legitimately changes the ExFAT allocation bitmap, appended
root entries, FAT entries for newly allocated clusters, and those new data
clusters. Instead, quick mode hashes a pinned concatenation of 145,815,472
source-bound bytes twice: both ExFAT boot regions, every original FAT entry,
the original root entries, and clusters 11 through 4,459 containing all three
payload directory trees and every payload byte. The exact raw ExFAT verifier
report proves that the original allocation set ends at cluster 4,459 and has
no overlaps or unclaimed allocations. Read-only
`fsck_exfat`, the three required payload roots, and the explicit macOS metadata
allowlist still gate success. A change to any original directory, payload
file, boot field, or FAT chain therefore fails even though known automount
metadata may be added after cluster 4,459.

The privileged audit creates its receipt as a root-owned direct child of the
ownership-enabled, sticky `/private/tmp`. It verifies that this directory is
on a physical disk other than the target card. Only after all receipt entries
are complete and validated are the regular files handed to the invoking user;
the top-level receipt directory is handed over last. The script never performs
a recursive `chown`. Copy the resulting small receipt to external evidence
storage after the command returns if long-term retention is needed.

Failure cleanup never opens, mounts, unmounts, or ejects a device path. The one
normal-path unmount occurs only after the whole disk, all three partitions,
both filesystem UUIDs, and the complete MBR ranges have matched. Therefore a
preflight failure cannot act on an unverified or re-enumerated `/dev/diskN`;
after any failure, treat card mount state as unknown and inspect it before
retrying.

A quick PASS is deliberately labeled:

- `audit_level=quick`;
- `p3_full_verified=false`;
- `p3_allocated_window_verified=false`;
- `p3_immutable_payload_verified=true`;
- `p3_verified_bytes=145815472`;
- `prior_full_write_verified=true`.

It is sufficient for the normal first-boot/bring-up gate because the complete
write transaction already read back every p3 byte once. It is not proof that
the currently inserted card's unallocated p3 capacity was reread during this
post-reinsert session.

### Full audit for storage suspicion or periodic qualification

Omitting `--audit-level` preserves the original full behavior; this is the
same as `--audit-level full`:

```bash
mainline/scripts/audit-debian13-new-card-after-reinsert.sh \
  --device /dev/diskN \
  --confirm-device /dev/diskN \
  --layout fast-card-62534975488 \
  --asset-manifest-sha256 HASH
```

Full mode reads 125,992,697,856 raw bytes. One claimed read-only raw descriptor
remains pinned while it hashes the prefix and p2 twice, p1 three times, the
complete p3 twice, and the 256 MiB snapshot window three times; runs read-only
FAT/ExFAT checks; verifies BOOT anchors and the exact three EASYROMS payload
directories; rechecks geometry and mount state; and ejects. Its receipt states
`p3_full_verified=true`.

Use full mode when a boot, filesystem, module, or payload failure points to
storage; after an unsafe unplug or I/O error; before treating a card as a new
long-term baseline; or periodically when qualifying the card/reader. Neither
mode repairs a filesystem. Only a final `AUDIT_COMPLETE`,
`safe_to_boot=true`, `card_state=ejected` receipt from the selected mode is
consumable.

The full p3 write plus full readback exercises every sector to the end of the
new card. This is stronger than copying the smaller p3 and merely extending the
partition table, which would neither resize ExFAT correctly nor test the added
capacity.

## 2026-08-15 cold-MMC qualification and later recurrence review

The first cold boot of this replacement card had one
`mmc0: error -84 whilst initialising SD card` and then succeeded on retry. That
same session completed a clean 1 GiB direct read; a warm reboot had no MMC or
ext4 fault. To distinguish a recurring initialization problem from a transient
first-use event, three later independent power-off cold boots used the unchanged
active v0.8 fallback and performed no card write or stress test.

All three later boots recorded the 400 kHz initialization step, the direct
transition to 150 MHz, `new ultra high speed SDR104 SDXC card`, the expected
58.2 GiB `mmcblk0`, p1/p2/p3 enumeration and normal p2 mount. Every final check
reported `ext4_errors=0` and zero failed systemd units. The two fully captured
runs additionally reported `fault_count=0` for the bounded MMC, EXT4 and JBD2
patterns. At the time, these three runs closed the requested qualification and
each ended after p2 was remounted read-only, all filesystems were unmounted and
`Powering off` was reached.

The first of these three logs attached at Linux uptime 4.9 seconds, so it does
not contain U-Boot or the initial live kernel stream. Its explicit post-login
dmesg replay does contain the complete timestamped MMC initialization and mount
sequence. The second and third logs start before power-on and cover U-Boot,
Linux, the same health query and shutdown. This closes the requested three-boot
qualification but is not a claim of lifetime media reliability. Later evidence
did reopen the gate as the contract required.

### Directly captured recurrence inventory

A 2026-08-17 review of every raw serial log containing the exact error found
five independent captures, not one isolated later event:

| `fast-card-firstboot-20260814T120439Z.bin` | v0.8 | 2.257158 s | 300 kHz, then SDR104 |
| `v010-audio-jack-20260815.bin` | v0.10 | 2.272630 s | 300 kHz, then SDR104 |
| `hantro-reference-20260816.bin` | v0.8 | 2.309711 s | 300 kHz, then SDR104 |
| `v010-rgui-rom-launch-20260817.bin` | v0.10 | 2.272375 s | 300 kHz, then SDR104 |
| `v010-charger-input-meter-20260817.bin` | v0.10 | 2.267993 s | 300 kHz, then SDR104 |

The last log is 63,828 bytes with SHA-256
`f8d068698b158847104ee4bef7b5c3c191c6db296b1b19d57b79d6e9dee56fd9`.
The other four hashes are already pinned by their owning result records and the
ledger. Multiple clean cold boots are interleaved with these failures. All five
failed first attempts identify the same 58.2 GiB SDXC card at address `0001`
after retry; every captured session reaches the expected partitions and none
shows a later MMC I/O or ext4 error. The event spans v0.8 and v0.10, so the
v0.10 ADC-only DT change is not a viable cause.

[Linux 6.12.99 MMC core](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/drivers/mmc/core/core.c?h=v6.12.99)
defines its removable-card initialization frequencies as 400, 300, 200 and
100 kHz. `mmc_rescan()` tries them in that order and powers the host down after
an unsuccessful attachment. In the
[DesignWare MMC host](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/drivers/mmc/host/dw_mmc.c?h=v6.12.99),
`-EILSEQ` (`-84`) can represent either a response-CRC failure or several data
CRC/end-bit failures; the
[generic SD attach path](https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/tree/drivers/mmc/core/sd.c?h=v6.12.99)
prints only the final number. The ordinary serial logs therefore prove an
initialization retry but cannot identify the failing command or distinguish
response from data. The later 150 MHz tuning and data path repeatedly work, so
this evidence does not justify disabling SDR104 or lowering the normal maximum
frequency.

### Bounded next cold-init contract

Do not run another blind cold-boot loop. The host side is complete: the narrow
error-only DesignWare diagnostic, exact v0.13 kernel/package and deterministic
p2 one-shot all passed their source and artifact gates. Their authoritative
hashes and staging procedure are in
[`../bringup-tests/V13-MMC-INIT-ONE-SHOT.md`](../bringup-tests/V13-MMC-INIT-ONE-SHOT.md).
The candidate does not change timing, voltage, frequency or request completion;
the active p1 and U-Boot environment remain unchanged. Never use `saveenv`.

For the single physical run, open serial at 1500000 before power and switch only
at the OP-TEE marker. Record whether USB-DC is absent or present; if present,
record inline voltage/current. Capture the complete 400 kHz attempt, any failed
request, the selected retry frequency, card identity, partition enumeration,
root mount, ext4 error counter and failed units. A clean boot without `-84` is
an **inconclusive diagnostic sample**, not permission to loop. A reproduced
`-84` is useful only if the added evidence identifies its request/error class.
End either outcome with `sync`, controlled poweroff and serial confirmation.

Keep the card accepted when the only fault remains the initial 400 kHz attempt,
300 kHz recovers, all partitions appear and later MMC/ext4 health stays clean.
Stop ordinary gaming work and escalate to an offline card audit only if the
retry also fails, a partition is missing, a later CRC/timeout/I/O error occurs,
or the ext4 error counter changes. Do not repeat the 125 GB audit based only on
the already bounded initialization signature.
